TrueSet: catch the data problems single-table checks miss

dbt tests, Great Expectations and Soda validate one table at a time. They cannot see a value that silently changed between two systems, or tell a real spike from a $2.9M error. TrueSet is the open-source library I founded to do exactly that, with every check written once and run on any engine.

How TrueSet works

01Why I'm building it

The most expensive data problems I have found in client work were not in any one table. $2.97M of revenue credited to the wrong place came from a join fallback four layers down. $2.17M of discounts were zeroed somewhere between the point-of-sale system and the warehouse. Every table on its own looked fine.

Catching that kind of break means checking one system against another, and the only open-source tool built for it, data-diff, was archived in 2024. So I built TrueSet: reconciliation as a first-class check, alongside the everyday ones, with the same definition running wherever the data is.

02What it does that others can't

Cross-system reconciliation. Prove a load against its source: counts agree, every key traces back, and the values themselves match. It reports every failure mode at once (changed values, keys missing on either side, duplicates), even when the two sides live on different engines.

checks:
  - type: row_count_parity
    reference: source
  - type: value_parity
    key: order_id
    columns: [amount, status]
    reference: source
    ref_key: id

Corroboration (newer, experimental). When an extreme value is often the truth (a demand spike, a market move), a fixed threshold cannot tell signal from mistake. TrueSet trusts a spike only if supporting signals agree: volume moved too, or a second independent feed shows the same thing. A lone spike gets surfaced.

  - type: corroboration
    column: price
    corroborate_with: [volume]
    severity: warn

03What ships today

  • Checks: not_null, unique, in_set, in_range, matches_regex, row_count, no_duplicate_rows, columns_exist and aggregate metrics.
  • Reconciliation: row_count_parity, referential_integrity and value_parity, across systems and engines.
  • Portability: one check runs unchanged on your warehouse as pushed-down SQL, with identical verdicts verified against a real Postgres.
  • Pipeline: run at ingestion, in flight or after load; failing rows go to a quarantine file with their reasons.
  • Governance: owner, sensitivity, regulation and tags on any check; reports by each; PII and PCI classification.
  • Monitoring: freshness, plus volume and metric anomalies against run history, with results kept as an audit trail.
  • Adoption: import existing dbt tests, profile and suggest checks from a sample, a GitHub Action, and pip install trueset.
One trust rule throughout: AI can draft and explain checks, but only deterministic, auditable code ever decides pass or fail. Validation stays reproducible.

04Where it already runs

TrueSet does the load reconciliation in my holdings data quality monitor, proving what was loaded against what the SEC published, and the data contracts in the claims platform, where exactly the 40 broken rows are quarantined with their reasons.

05What's next

  • Thresholds that set themselves: limits calibrated from a data sample ship today; learning normal ranges from run history and per segment is next.
  • AI failure diagnosis: explaining why a check failed, on top of the deterministic result, plus suggested sensitivity and ownership tags for columns no pattern catches. Suggested and human-reviewed, never applied automatically.
  • Data contracts: named, versioned suites bound to a dataset, with an owner and an SLA.

The full list lives in the public roadmap. Feedback and early users are very welcome.
