Who’s burning the Snowflake bill?

When analytics is decentralised, dozens of people and service users run queries on shared Snowflake warehouses. The bill arrives per warehouse, not per person, so when it jumps nobody knows who to talk to. This project attributes every credit to the query, user and team that caused it, and runs every day in production: Airflow on AWS Fargate, reading a live Snowflake account.

01The problem

Snowflake bills for the time a warehouse is running, including the idle tail before it auto-suspends. Snowflake’s own QUERY_ATTRIBUTION_HISTORY leaves idle time out, so attributing cost per user alone can hide most of the bill.

And showback that people cannot reconcile to the bill gets argued with, not acted on. Every credit has to land somewhere, and the total has to match the invoice.

The Snowflake account is set up like a decentralised analytics team: 8 analysts across finance, risk, marketing and operations, a BI service account refreshing a dashboard, and a transform service account rebuilding a daily model. They run as a scripted workload on three warehouses, each user signing in with its own key and tagging its queries. The queries, the metering and the bill are real.

02What I built

  • Query x hour slices, so a long query is split across the clock hours it ran in.
  • Warehouse busy time as the union of query time, so concurrent queries are not double counted. Idle time is billed running time minus busy time.
  • Query cost: each hour’s active credits are shared by its queries in proportion to execution seconds, and idle credits stay with the warehouse instead of being smeared across users.
  • Showback by user, team and workload, in credits and USD, with alerts for a team week-over-week spike, a warehouse idle share over 25%, and any workload over 10% of spend.
  • Five checks run on every build: the reconciliation to the bill, one row per query, every query costed, no negative or null costs, and busy time never more than running time. Four tests check the checks, including that the planted problems are flagged and that a rebuild gives the same numbers.
  • Production on AWS: EventBridge Scheduler starts an ECS Fargate task each morning. It runs the Airflow DAG (extract from ACCOUNT_USAGE, one task per model, a reconciliation gate, publish), writes the showback to S3 and emails an SNS alert if any step or check fails. The Snowflake key lives in Secrets Manager, and IAM is least-privilege.
  • Terraform for both clouds: warehouses, a role per team, key-pair service users and grants in Snowflake (67 resources); the runtime, storage, secrets and schedules in AWS (21). An account-level resource monitor caps spend.

On the live account, almost the whole bill was warehouses running with nothing to do. The dashboard refreshes every 5 minutes, but its warehouse waits 600 seconds before suspending, so it never suspends. A per-query cost view would have shown about 1% of this bill and hidden the rest. The fixes are auto-suspend per warehouse and fewer, busier warehouses for sporadic ad hoc users, not asking analysts to write cheaper SQL.

Before going live, the models were tested on a seeded four-week sample (9,451 queries) with planted problems: an overnight dashboard refresh, an hourly unfiltered scan and a team spike. All three were caught.

04What real data broke

The sample passed every check. The first live run failed the reconciliation gate, which is the gate doing its job. Real ACCOUNT_USAGE had three things the sample did not:

  • Empty warehouse sizes on some queries in QUERY_HISTORY, for example while a warehouse resumes. Joining on size duplicated warehouse-hours and broke reconciliation.
  • Snowflake’s serverless pools appear in query history but bill through serverless metering, so they can never match warehouse metering. They are now scoped out explicitly.
  • DDL and metadata statements (CREATE USER, GRANT, SHOW) report a warehouse but run in cloud services, in hours with zero compute credits. They are now costed at zero instead of going missing.
