QA for AI training data: rules, planted defects and an LLM judge

Models that call tools learn from conversations: a user asks, the model picks a tool, fills its arguments, reads the output and answers. If that training data is wrong, the model learns to be wrong. I built a reusable QA pipeline that turns “good data” into checks you can measure.

Independent project
Data

01The problem

The dataset, glaive-function-calling-v2, has 112,960 conversations under Apache-2.0. Reading them by hand does not scale, and simple rules only see structure. A rule can tell that an argument is missing; it cannot tell that “Paris” was never what the user asked for.

So the question was not just “what is wrong with this data?” but “how much of what is wrong can each layer of checking actually catch?”

02What I built

  • 12 rule checks, cheap enough to run on every row: schema validity, turn order, malformed calls, unknown tools, missing or unknown arguments, types and enums, unterminated turns, numbers not grounded in the tool output, answers that ignore the tool output, refusals when a matching tool exists, and unacknowledged tool errors. Each has a unit test that plants exactly one defect.
  • A planted-defect benchmark: 150 copies of clean conversations, each with one known defect, to measure what each layer catches.
  • LLM-as-a-Judge on the Claude API with structured output validated by Pydantic, grading tool selection, argument fidelity, grounding, completeness, and helpfulness and honesty. Each verdict carries a failure-mode label and the evidence span, so it can go straight back to a data vendor.
  • What broke along the way: the first grounding rule flagged 59 false positives on paraphrased answers. I redesigned it around word overlap and numeric matching, which left 5.

Wrong function name100%

Conversation truncated100%
Number in answer altered92%

Plausible but wrong argument value0%

The bigger risk is low diversity, not broken rows. “Can you order a pizza for me?” appears 99 times, and a model trained on this mix over-learns refusing.

The benchmark shows exactly where rules stop: 100% recall on structural defects and 0% on plausible but wrong argument values. That gap is the case for a judge, and the judge is scored on the same planted set, like any other check, rather than trusted blindly.

Stated plainly: the published report’s judge section is a dry run. The 272 judge requests are built and saved in the repository; judge recall and false-positive numbers are filled in by running it with an API key.
